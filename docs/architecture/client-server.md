# Client-server protocol

The `aerospace` binary is a thin client: it validates args, ships them to `AeroSpace.app` over a
Unix-domain socket, and reproduces the server's stdout, stderr and exit code. Every scripted
integration (status bars, `exec-*` callbacks calling back into `aerospace`, third-party clients)
depends on this path.

**History:** upstream's `git log` for these paths; `dev-docs/architecture.md` (upstream, stale);
the user-facing protocol spec is the "Socket protocol" section of `docs/guide.adoc`.

- `Sources/Cli/_main.swift`: the whole client: top-level flags, local parse, connect, stdin, request, print, exit; `runSubscribe`.
- `Sources/Cli/cliUtil.swift`: client version string, `hasStdin()` (stdin is not a TTY).
- `Sources/Cli/subcommandDescriptionsGenerated.swift`: the `SUBCOMMANDS:` table in `aerospace --help`, generated by `generate.sh`.
- `Sources/Common/model/clientServer.swift`: `SOCKET_PROTOCOL_VERSION`, `ClientRequest`, `ServerAnswer`.
- `Sources/Common/util/NWConnectionEx.swift`: handshake (`initConnection`) and framing (`writeAtomic`, `readNonAtomic`, `readTillError`) on `NWConnection`, used by both sides.
- `Sources/Common/util/commonUtil.swift`: `socketPath`.
- `Sources/AppBundle/server.swift`: `startUnixSocketServer`, the per-connection loop `newConnection`, and `toggleReleaseServerIfDebug`.
- `Sources/AppBundle/subscriptions.swift`, `Sources/AppBundle/model/ServerEvent.swift`: `subscribe` registry, `broadcastEvent`, event payloads.

## How it works

### Socket path

`socketPath` (in `Sources/Common/util/commonUtil.swift`) is built from `aeroSpaceAppId` and
`unixUserName` (`NSUserName()`):

    /tmp/<aeroSpaceAppId>-<unixUserName>.sock

`aeroSpaceAppId` (`Sources/Common/appMetadata.swift`) is `bobko.aerospace` in non-DEBUG builds and
`bobko.aerospace.debug` under `#if DEBUG`. The CLI and server pick it at compile time, so a debug
CLI (the one in `.debug`) only reaches a debug server and a release CLI only a release server.

The server (`startUnixSocketServer`) deletes whatever file is at the path, then binds an
`NWListener` with `NWParameters.tcp` and `requiredLocalEndpoint = .unix(path:)` (a stream socket;
"tcp" is just Network.framework's stream protocol choice). Listener creation failure is fatal
(`getOrDie`). It's started from `initAppBundle()` only after Accessibility permission is granted
and the config is loaded, so CLI calls made before that fail to connect.

### Wire format

All integers are `UInt32` written with `withUnsafeBytes`, i.e. host byte order (little-endian on
both supported archs).

1. Handshake (`initConnection` on the client, top of `newConnection` on the server). The client
   waits for the connection to reach `.ready` (or fails on `.failed`/`.waiting`), writes its
   `SOCKET_PROTOCOL_VERSION` (currently `1`), and reads the server's. The server reads the client
   version, always writes its own, then closes if they differ. A mismatch on the client side
   becomes `InitConnectionError.customError` with a "restart AeroSpace" message.
2. Frames. Every message after the handshake is `UInt32 length` + that many bytes of JSON.
   `writeAtomic` encodes and sends length+payload in one `send`; `readNonAtomic` reads the 4-byte
   length then loops `receive` until it has the payload. There is no maximum frame size and no
   read timeout on either side.

`ClientRequest` is `{args: [String], stdin: String, windowId: UInt64?, workspace: String?}`.
`windowId`/`workspace` are double optionals so the encoder emits explicit `null`; the custom
decoder distinguishes "key absent" (`nil`) from "key present, null" (`.some(nil)`). The legacy
`command` key is ignored. `ServerAnswer` is `{exitCode: Int32, stdout, stderr, serverVersionAndHash}`.
Decoding of old request shapes is pinned by `Sources/AppBundleTests/model/ClientServerTest.swift`.

### Client flow (`Sources/Cli/_main.swift`)

1. No args: usage to stderr, exit 2. `-h`/`--help`: usage to stdout, exit 0. Neither connects.
2. `-v`/`--version`: connects and sends a request with empty `args`. The server answers it with
   a parse failure (or a "server disabled" message), and the client only reads
   `serverVersionAndHash` from that answer. Prints both versions, warns on stderr if they differ,
   exits 0 even when the server isn't running (prints "Unknown. The server is not responding").
3. `parseCmdArgs(args)` from `Common`: parse errors exit with the command's code and message;
   `--help` on a subcommand prints help and exits 0. `true`/`false` short-circuit here and exit
   0/1 without connecting. The parsed value is used only for local decisions (fail exit code,
   stdin, subscribe); the raw `args` array is what gets sent.
4. Connect. On a Network error: "Can't connect to AeroSpace server. Is AeroSpace.app running?"
   plus the NW error, exit with the command's `failExitCode` (2 for most commands).
5. stdin is read only with `--stdin`, or in the legacy implicit case (`workspace`/
   `move-node-to-workspace` with a relative target and non-TTY stdin), which now errors unless
   `--stdin`/`--no-stdin` is explicit. More than 1000 lines exits with an error.
6. `AEROSPACE_WINDOW_ID` and `AEROSPACE_WORKSPACE` from the environment go into the request.
   The server sets these when it runs callbacks, so nested `aerospace` calls act on the triggering
   window/workspace.
7. Send, read one answer, `print` stdout and `eprint` stderr if non-empty (each gains a trailing
   newline), and `exit(answer.exitCode)`. If the exit code is non-zero and the server's
   version+hash differs from the client's, a mismatch warning is appended to stderr.

### Server flow (`newConnection` in `Sources/AppBundle/server.swift`)

Each accepted connection gets its own unstructured task; `newConnection` is nonisolated, so
reading and JSON decoding happen off the main thread. After the handshake it loops, so one
connection may carry many requests (the bundled CLI sends one; a custom client can reuse the
connection and skip the per-call connect and handshake):

1. `readNonAtomic`; a read error is answered with exit 2 and ends the connection. Undecodable JSON
   is answered with exit 2 and the loop continues.
2. `args.first == "subscribe"` is handled before anything else (see below).
3. `parseCommand(request.args)`: the same `Common` parser plus `toCommand()`.
4. `RunSessionGuard.isServerEnabled(orIsEnableCommand:)` (main actor): when the server is
   disabled via `enable off`, everything except `enable` gets exit 2 "server is disabled".
5. Help and parse failures are answered directly. A command runs inside
   `runLightSession(.socketServer(args), token)` with `CmdEnv(windowId:, workspaceName:)` from the
   request; `CmdResult.stdout`/`stderr` lines are joined with `\n`; errors thrown by the session
   come back as the command's fail exit code with "Fail to await main thread".
6. If the request lacked the `windowId` or `workspace` key entirely, a note asking the client to
   forward the env vars is appended to stderr (aimed at third-party clients).

### subscribe

Same socket and framing. The client sends one `ClientRequest` with `args` starting with
`subscribe`, then loops `readNonAtomic` and prints each frame's JSON as one line with an explicit
`fflush`; any read error exits with the fail code. The server parses it with
`parseSubscribeCmdArgs` (`Sources/Common/cmdArgs/impl/SubscribeCmdArgs.swift`) and calls
`handleSubscribeAndWaitTillError` on the main actor: it registers the connection in `subscribers`,
sends initial events unless `--no-send-initial` (focus, workspace, mode, focused monitor; never
`window-detected` or `binding-triggered`), then awaits `readTillError` until the client hangs up.
`subscribe` bypasses `parseCommand`, the server-enabled check and `runLightSession`, so it works
while the server is disabled and costs no refresh. `subscribe` inside `eval` is rejected.

`broadcastEvent` (called from `Sources/AppBundle/focus.swift`, `Sources/AppBundle/config/HotkeyBinding.swift`,
`Sources/AppBundle/tree/MacWindow.swift`) starts a main-actor task per event that writes to each
matching subscriber in turn, awaiting each send; a failed write drops that subscriber. Events are
encoded with sorted keys and unescaped slashes.

### Debug server and the release server

`toggleReleaseServerIfDebug` is a second, internal client: in DEBUG builds the server connects to
the release socket (`stableAeroSpaceAppId`) at startup and sends `enable off`, and its termination
handler (`Sources/AppBundle/util/appBundleUtil.swift`) sends `enable on`, so a running release
AeroSpace stops managing windows while you run `run-debug.sh`. Skipped with `--read-only`.

## Performance notes

- Every `aerospace` call is a process launch that loads Foundation, Network and AppKit (`Common`
  imports AppKit), then two socket round trips: handshake, then request/answer.
- The server executes commands on the main actor with no queue of its own, so two requests can
  interleave at `await` points. Every command that reaches step 5,
  including read-only queries like `list-windows` or `list-workspaces`, goes through
  `runLightSession`: native focused-window lookup over AX, two model refreshes, `layoutWorkspaces`
  (applies frames to visible windows and re-hides invisible ones), a macOS focus sync if focus
  changed, and finally `scheduleCancellableCompleteRefreshSession`, which queues a full refresh of
  all apps' windows. A status bar polling the CLI therefore triggers a layout pass and a full
  refresh per poll; the next light session cancels a pending full refresh, but a steady poll
  keeps rescheduling it. See layout-and-refresh.md.
- There's no client-side timeout. If a call's session is stuck (e.g. awaiting an unresponsive app's
  AX thread), that CLI call hangs until it frees up.
- `subscribe` is the cheap alternative to polling: events are pushed from existing code paths
  without a refresh session.

## Rules worth keeping

- Keep both sides on the same framing helpers in `Sources/Common/util/NWConnectionEx.swift`.
  Third-party clients implement the format from `docs/guide.adoc`, so any change to handshake,
  byte order or JSON field names is a protocol break: bump `SOCKET_PROTOCOL_VERSION` and update
  the guide section.
- `ClientRequest` decoding must keep accepting old shapes (no `windowId`/`workspace`, extra
  `command`). Old CLIs and scripts talk to new servers after upgrades until the app restarts;
  `ClientServerTest` pins this.
- Args are parsed twice with the same `Common` parser. A new flag that only one side understands
  is either rejected by the client before sending or by the server after; add parsing in
  `Sources/Common/cmdArgs/`, never in `Sources/Cli/`.
- Client-only behaviour (stdin reading, `true`/`false` short-circuit, subscribe streaming) is
  keyed on the parsed type in `Sources/Cli/_main.swift`. A command that needs client-side work must
  be special-cased there too.
- The socket path depends on `#if DEBUG`. When testing a debug server, use the debug CLI
  (`run-cli.sh`, or `aerospace` in `.debug`); the installed `aerospace` talks to the release app.
- `run-cli.sh` rebuilds (`build-debug.sh`, which also runs `generate.sh`) on every call, so don't
  use it to time CLI latency; call the `aerospace` binary in `.debug` directly.
- The server answers `-v` from the client with whatever an empty-args request produces; don't make
  empty `args` fatal or the version check breaks.
